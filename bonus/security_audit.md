# Проверка безопасности API (п. 5 ТЗ)

В рамках бонусного задания было проверено, что можно узнать, обойти или подделать через запросы к API (`https://kvitto-qa-demo.vercel.app/api`).

Ниже результаты практической проверки через Postman и DevTools:

---

## 1. Подмена данных и суммы платежа через ID (Base64)
* **Что обнаружено:** При успешном создании платежа сервер возвращает параметр `id`, например:
  `eyJ0Ijoic3RhbmRhcmQiLCJhIjoxOTkwMCwibSI6ImNhcmQiLCJpbSI6bnVsbCwiZSI6Iml2YW5AZXhhbXBsZS5jb20ifQ`
* **Как проверено:** Строка начинается на `eyJ` — это стандартный признак строки Base64. При декодировании через консоль браузера командой `atob(...)` открывается обычный JSON:
  ```json
  {"t":"standard","a":19900,"m":"card","im":null,"e":"ivan@example.com"}
  ```
* **В чём уязвимость:** 
  Если изменить сумму `"a": 19900` на `"a": 1` (1 рубль) и закодировать строку обратно в Base64 через `btoa(...)`, а затем запросить этот платёж через `GET /api/payments/{поддельный_id}`, сервер возвращает статус **`200 OK`** со стоимостью 1 рубль!
* **Вывод и рекомендация:** Сервер не хранит платежи в базе данных и не подписывает ID криптографической подписью. Любой пользователь может вручную сгенерировать ссылку с суммой 1 рубль и показать её как подтверждение оплаты. Бэкенд обязан самостоятельно определять стоимость заказа из базы данных по строго валидированному `tariff_id` и рассчитывать сумму на сервере, а не доверять незащищенному клиентскому состоянию.

---

## 2. Создание платежа с несуществующим тарифом и суммой `null`
* **Что проверено:** Отправлен запрос `POST /api/payments` с выдуманным тарифом: `"tariff_id": "super_vip"`.
* **Результат:** Сервер не проверяет список существующих тарифов (`basic`, `standard`, `premium`) и возвращает статус `200 OK` с телом:
  ```json
  { "tariff_id": "super_vip", "amount": null, "status": "pending" }
  ```
* **Вывод:** В систему можно отправить «битый» заказ с пустой суммой (`null`), что может сломать интеграцию с онлайн-кассой или ОФД.

---

## 3. Падение сервера с ошибкой 500 (Internal Server Error)
* **Что проверено:** Отправка `POST /api/payments` с пустым JSON-телом `{}` или без обязательного поля `phone`.
* **Результат:** Вместо понятной ошибки валидации `422 validation_error` сервер падает с кодом **`500 Internal Server Error`** (`{"error": "internal_error"}`).
* **Вывод:** Бэкенд не перехватывает ошибки при отсутствии обязательных полей. На проде это может приводить к падению серверных процессов при некорректных запросах.

---

## 4. Проверка на инъекции (SQL-инъекции и XSS)
* **Что проверено:** В поля `name` и `email` отправлялись тестовые строки со спецсимволами:
  * `<script>alert(1)</script>`
  * `' OR '1'='1`
* **Результат:** Сервер корректно отклоняет такие запросы с кодом `422 Unprocessable Entity` («Укажите имя и фамилию»). Прямой уязвимости к XSS и SQL-инъекциям через данные поля не обнаружено.
